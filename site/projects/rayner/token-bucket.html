How does a token bucket let a burst through but refuse a flood?

A server shares its work among many clients, so it limits each one: a request it serves gets 200, OK, and one it refuses gets 429, Too Many Requests, which tells the client to slow down. A short burst should still get through. So the server keeps a balance of tokens for the client, at most five: the bucket. Each accepted request spends one token; a request that finds less than one gets 429. Capacity sets the burst the client can save; refill rate sets how quickly it earns another request. The dashed line marks the one token a request needs. How many of six simultaneous requests can spend this balance?

Check yourself

  1. At 4 tokens a second, R9 leaves 1 token and R10 arrives four seconds later. How many tokens does R10 find, and why not 17?

    Show the answer

    Five. Four seconds at 4 a second would add 16, but min(5, …) stops the balance at the bucket’s five and throws the rest away.

  2. At 2 tokens a second, R8 and R9 arrive at the same instant. Why does R8 get 200 and R9 get 429?

    Show the answer

    The half second since R7 added exactly one token, and R8 spent it. No time passes between R8 and R9, so nothing is added and R9 finds 0.

  3. At 1 token a second, what does R7 find half a second after the burst?

    Show the answer

    Half a token: 0.5 s × 1 a second. That is less than the one token a request needs, so R7 gets 429.

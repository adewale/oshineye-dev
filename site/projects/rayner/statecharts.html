What is a statechart, and why use one instead of a state machine?

This coffee machine is always in exactly one of four boxes: idle, grinding, brewing or ready. Each event moves it along one of 4 arrows: START, GROUND, BREWED and TAKE. The boxes are called states, the arrows transitions, and the whole drawing a state machine. Now give it a power button: the event POWER_OFF switches it off from whichever state it is in, and POWER_ON switches it back on.

  2. A POWER_OFF copied onto every state, and one copy missed

    Predict: the marked arrows all do the same thing. How could one arrow do the job?

    In a plain state machine an arrow leaves exactly one state, so idle, grinding, brewing and ready each need their own POWER_OFF, and off needs a POWER_ON: 5 more arrows, 9 in all. Copied by hand, one is easy to miss. In this hand-copied machine brewing’s is missing, so pressing the power button while brewing does nothing until the brew is done, and a state added later would need a copy of its own. The same event leading from several states to the same place is the first of two signs to look for in a flat machine.

    • off; idle; grinding; brewing; ready; start → off; off → idle: POWER_ON; idle → off: POWER_OFF (marked); idle → grinding: START; grinding → off: POWER_OFF (marked); grinding → brewing: GROUND; brewing → ready: BREWED; ready → off: POWER_OFF (marked); ready → idle: TAKE; brewing → off: POWER_OFF missing (marked).
  3. A box around the four states takes the one POWER_OFF

    In XState and SCXML, the current state is asked first, then the box around it.

    Put the four in a box called on, and give the box the one POWER_OFF: the 9 transitions a complete flat machine needs become 6. The shared rule is written once on the parent rather than copied onto each child. When POWER_OFF arrives while brewing, brewing is asked first; it has no POWER_OFF arrow, so the box around it, its parent, takes the event. The box is half of the answer: a statechart is a state machine whose states can contain other states, active one at a time or several at once. Inside on, one state is active at a time; the next machine needs several at once.

  4. A media player: two on/off features make four flat states

    Predict: playback and volume never affect each other. What if each had its own small machine?

    A media player is playing or paused, and separately muted or unmuted; neither choice limits the other. A plain state machine is in one state at a time, so each state must name both: four combinations, which with off make 5 states and 13 transitions. Changing playback needs the same transition in both volume settings, and changing volume repeats it for both playback settings. Each further independent on/off feature doubles the combinations. Every name is two words, one per feature, and every arrow between them changes one word and keeps the other. States named by two independent words are the second sign.

  5. Split the box on into two small machines, called regions

    Predict: can a statechart do anything a state machine can’t?

    Draw a dashed line through on and give each side one feature: the grid’s words slide apart, and playing · muted becomes playing on one side and muted on the other. Each side is a region, a small machine in one state at a time, and both run at once. A flat state had to name both features at once; a state in a region names only its own, so a further feature adds a region of two states where the flat machine doubles.

    Flatten the player and send the same events through both machines.

    Each row sends the next event to the statechart and to its flat version, and both end in the same states. At run time the player is still in one combination of playback and volume. Only the drawing changes: the statechart describes each feature separately, while the flat machine repeats it for the combinations. The possible combinations still exist; writing their shared behaviour once is what saves space.

    A flat machine would need 9 states and 25 transitions; the statechart draws 8 arrows.

    In a flat machine every state while on would pair one of the four brewing states with still or frothing, like grinding · frothing, all 8 pairs reachable, and every arrow between them would change one word and keep the other: the second sign. So the frother goes in a second region inside on, and on’s one POWER_OFF covers both regions. Check yourself

  1. Give the frother its own power, so FROTH and STOP work whether the coffee machine is on or off. Where does the frother region go now, and how many states does the flat machine need?

    Show the answer

    Outside on, beside the whole machine: since the frother works whether the machine is off or on, it becomes a region next to the off-and-on machine, and the statechart’s top level splits in two. Flat, every one of the machine’s 5 states pairs with still or frothing, off included: 10 states where the frother inside on needed 9.

  2. Now the frother runs on the brewing steam, so it can be still or frothing only while brewing, and leaving brewing stops it. Write the flat machine’s state names. Does the second sign still say “region”, and where does the frother go?

    Show the answer

    The names are off, idle, grinding, brewing · still, brewing · frothing and ready: 6 states. Only the brewing states have two words, so the words are not independent and the second sign does not apply. The frother goes inside brewing as a box of two states, which makes brewing a parent: the first idea again. The statechart draws 8 transitions where the flat machine draws 13.

  3. In the last step the machine is grinding while the frother is frothing. Press POWER_OFF, then POWER_ON. Is the frother still frothing?

    Show the answer

    No. POWER_OFF is taken by on, which leaves both regions; POWER_ON enters on again, and each region starts at its start dot: idle and still. Nothing in the chart remembers where a region was when the machine went off.

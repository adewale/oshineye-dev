Why can a cancelled meeting remain in a guest’s calendar?

Alice cancels one meeting of her weekly stand-up. Bob, invited to that meeting alone, can still find it in his calendar, marked cancelled. To see why, start with how Alice’s app stores the series: as one VEVENT, the iCalendar record for an event. DTSTART is the first meeting, Monday 2 November 2026 at 09:00 UTC. RRULE repeats it weekly, and COUNT=6 stops after six meetings, with DTSTART counting as the first. The list shows the meetings a calendar computes from those two lines.

  5. One UID: at most one master, any number of overrides

    At a line’s end, a bar is one, a circle zero, a crow’s foot many.

    The storage rules explain why Bob can keep one occurrence without Alice’s master rule. Marks at a line’s ends say how many: a bar is one, a circle zero, a crow’s foot many. RFC 4791 puts every VEVENT with one UID in one calendar object: the master, which it defines as the one without RECURRENCE-ID, and the overrides, which may be stored without it, as Bob’s is.

      • EXDATE: excluded (datetime).

  7. The server refuses a second master or a second RRULE

    It answers 415, though RFC 5545 says just that RRULE SHOULD NOT repeat.

    Baïkal, running sabre/dav, checks each object saved to it and answers 415 to two VEVENTs without RECURRENCE-ID or to two RRULEs in one VEVENT. RFC 5545 recommends against a repeated RRULE, saying it SHOULD NOT occur, but does not forbid it; sabre is stricter, so the RRULE line now allows at most one. Bob’s copy, with no master, is accepted.

RFC 4791 puts every VEVENT with one UID in one calendar object: the master, which it defines as the one without RECURRENCE-ID, and the overrides, which may be stored without it, as Bob’s is.

    • ER diagram: 5 entities, 5 relationships:
      • CALENDAR_OBJECT → MASTER: holds (each CALENDAR_OBJECT has zero or one MASTER, each MASTER has exactly one CALENDAR_OBJECT);
      • CALENDAR_OBJECT → OVERRIDE: holds (each CALENDAR_OBJECT has zero or more OVERRIDE, each OVERRIDE has exactly one CALENDAR_OBJECT);
      • MASTER → OVERRIDE: is overridden by (each MASTER has zero or more OVERRIDE, each OVERRIDE has zero or one MASTER);
      • MASTER → EXDATE: skips (each MASTER has zero or more EXDATE, each EXDATE has exactly one MASTER);
      • MASTER → RRULE: repeats by (each MASTER has zero or more RRULE, each RRULE has exactly one MASTER);
      • CALENDAR_OBJECT: UID (text);
      • MASTER: DTSTART (datetime);
      • OVERRIDE: RECURRENCE-ID (datetime), DTSTART (datetime);
      • RRULE: FREQ (text), COUNT (int);
      • EXDATE: excluded (datetime).
  7. The server refuses a second master or a second RRULE

    It answers 415, though RFC 5545 says just that RRULE SHOULD NOT repeat.

    Baïkal, running sabre/dav, checks each object saved to it and answers 415 to two VEVENTs without RECURRENCE-ID or to two RRULEs in one VEVENT. RFC 5545 recommends against a repeated RRULE, saying it SHOULD NOT occur, but does not forbid it; sabre is stricter, so the RRULE line now allows at most one. Bob’s copy, with no master, is accepted.

    • ER diagram: 5 entities, 5 relationships:
      • “a second one: 415” beside MASTER: DTSTART (datetime) (note);
      • “a second one: 415” beside RRULE: FREQ (text), COUNT (int) (note);
      • CALENDAR_OBJECT → MASTER: holds (each CALENDAR_OBJECT has zero or one MASTER, each MASTER has exactly one CALENDAR_OBJECT);
      • CALENDAR_OBJECT → OVERRIDE: holds (each CALENDAR_OBJECT has zero or more OVERRIDE, each OVERRIDE has exactly one CALENDAR_OBJECT);
      • MASTER → OVERRIDE: is overridden by (each MASTER has zero or more OVERRIDE, each OVERRIDE has zero or one MASTER);
      • MASTER → EXDATE: skips (each MASTER has zero or more EXDATE, each EXDATE has exactly one MASTER);
      • MASTER → RRULE: repeats by (each MASTER has zero or one RRULE, each RRULE has exactly one MASTER);
      • CALENDAR_OBJECT: UID (text);
      • MASTER: DTSTART (datetime);
      • OVERRIDE: RECURRENCE-ID (datetime), DTSTART (datetime);
      • RRULE: FREQ (text), COUNT (int);
      • EXDATE: excluded (datetime).

Check yourself

  1. Alice skips the fifth meeting, Monday 30 November, instead of Bob’s, by adding EXDATE:20261130T090000Z. How many meetings does her calendar show, and when is the last? What does Bob’s calendar show?

    Show the answer

    Alice’s shows five, the last still on Monday 7 December: COUNT=6 counts the excluded start, so the series does not run a week longer. Bob is still in the third meeting’s override, so any update the server sends him carries that override again, and his calendar keeps Monday 16 November, not cancelled.

  2. Alice moves the second meeting, which Bob does not attend. Before trying that setting: does Bob’s copy change, and why?

    Show the answer

    No. The iTIP REQUEST the server sends him holds only the VEVENTs he attends, the third meeting’s override, so his copy keeps that one VEVENT and never learns of the move.

  3. Bob’s calendar app wants to show him the rest of the stand-up series. Which lines would it need that his stored copy lacks?

    Show the answer

    The master’s DTSTART and RRULE. His copy holds one override and no masters, so it has no rule to generate the other weeks from; only the organiser’s object has one.

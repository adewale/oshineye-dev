Main history: Main makes its own commit

  1. Both branches moved on. Can a merge just move main to B?

    Predict: if the main label moved to B, which edit would main lose?

    Both branches started at A, where colour.txt is blue. On feature, B made it green; on main, commit C added title.txt, Home. We have main checked out (HEAD), so the files below are C’s. A branch label names a commit; arrows lead back through its history. Could moving main to B combine the edits?

    • A. B. C. feature. main. HEAD. File. Working contents. colour.txt. blue. title.txt. Home. Arrows point from a commit to its parent.
  2. Answer: the Home edit. No branch would reach C

    B’s history is B, then A; C is not in it.

    With main on B, checking out main gives green and no title.txt. B’s history is B, then A, so neither branch would contain C or the Home edit. C is still stored: moving the label does not delete the commit. To keep main’s history, following parent arrows from its new destination must still reach its old commit. A merge needs a new commit when each branch has a commit the other lacks.

    • A. B. C. feature. main. no branch. HEAD. File. Working contents. colour.txt. green. title.txt. absent. C is outside both branch histories.
  3. So git merge writes M, a commit with two parents

    Predict: if main had never made C, would Git still need M?

    git merge feature creates M with parents C and B and moves main to it. M’s files have both edits, green and Home, because the two edits touch different files. Feature stays at B, and C stays in main’s history.

    • A. B. C. M. feature. main. HEAD. File. Working contents. colour.txt. green. title.txt. Home. M records parents C and B.
  4. Answer: no. Without C, main just moves to B

    A is in B’s history, so moving main to B loses nothing.

    Here main never made C and still points at A, B’s parent. git merge feature moves main to B without a new commit, which Git calls a fast-forward, and colour.txt turns green. Git fast-forwards by default; the option --no-ff would make a merge commit here anyway, by choice, though no edit would be lost without one.

    • A. B. feature. main. HEAD. File. Working contents. colour.txt. green. title.txt. absent. main moves to existing commit B.

Main history: Main stays at the shared commit

  1. Only feature moved on. Can a merge just move main to B?

    Predict: if the main label moved to B, would main lose anything?

  2. Answer: nothing. git merge just moves main to B

    Predict: if main had made its own commit first, would moving the label still do?

    Main’s commit, A, is B’s parent, so B already holds everything main had. git merge feature moves main from A to B without a new commit, which Git calls a fast-forward and does by default, and colour.txt turns green. A merge needs a new commit when each branch has a commit the other lacks; here only feature does.

    • A. B. feature. main. HEAD. File. Working contents. colour.txt. green. title.txt. absent. main moves to existing commit B.
  3. Answer: no. With C on main, the merge needs M

    M has parents C and B, so main keeps both edits.

    Here main made C, adding Home. B does not contain C, so moving main to B would drop that edit from main’s history. git merge feature creates M with parents C and B, keeping green and Home. --no-ff can request a commit even when a fast-forward could keep both histories.

Check yourself

  1. After M is made, stay on main and run git merge feature again. Does main move back to B, make another commit, or stay at M?

    Show the answer

    It stays at M. B is already in M’s history, so Git reports Already up to date. Main has already incorporated feature; moving main back to B would discard C from main’s history.

  2. After M is made, switch to feature and run git merge main, with fast-forwards allowed. New commit, fast-forward, or no change?

    Show the answer

    Fast-forward. Feature is at B, which is already one of M’s parents, while main has commits feature lacks. Git moves feature from B to M without making a commit.

  3. Start again with feature at B and main at M. On feature, run git merge --no-ff main. Could Git fast-forward, and what does this option ask it to do instead?

    Show the answer

    A fast-forward would be possible because B is in M’s history. --no-ff asks Git to create a merge commit anyway, with B as its first parent and M as its second. The history makes a fast-forward possible; the chosen merge policy decides whether to use it.

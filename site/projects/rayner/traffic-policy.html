How does traffic policy divide requests among pods?

A Service of type LoadBalancer: a cloud load balancer sends outside requests to the nodes, and rules that kube-proxy writes on each node hand every request to a pod. Node 1 runs 3 pods, Node 2 runs 1 and Node 3 runs none. The Service’s externalTrafficPolicy sets which pods a node may pick: under Cluster, the default, any pod in the cluster; under Local, only the pods on that node. This one is set to Local.

  2. Under Local, each node’s rules list only its own pods

    Probabilities 1/(n−i) give each pod 1/3 of the node’s requests.

    In iptables mode kube-proxy tries one rule per pod in order. For three candidates, the first takes 1/3 of requests; the second sees the remaining 2/3 and takes half of those, another 1/3 overall; the last gets the remaining 1/3. In general, rule i of n matches 1/(n−i) of the requests that reach it, counting i from zero, so each pod gets 1/n of the node’s traffic. Under Local Node 1 lists only its 3 pods: 1/3, 1/2, always, so each gets 1/3 of what Node 1 receives.

  3. Node 3 runs no pod, so it fails the health check

    Node 1 and Node 2 answer 200 and each get 1/2 of requests.

    Under Local, kube-proxy answers the load balancer’s health check on each node: 200 when the node runs a pod of the Service, 503 when it runs none. The load balancer stops sending to Node 3. It divides requests equally among healthy nodes, regardless of their pod counts, so Node 1 and Node 2 each get 1/2 of the requests. The next choice happens inside each node: its share is divided among its own pods.

    The shares are long-run averages for kube-proxy’s iptables mode; IPVS mode defaults to round robin. kube-proxy’s health check reports each node’s pod count in a header, but the docs warn that some cloud load balancers cannot weight nodes. Topology-aware routing and session affinity are left out.

    • Architecture diagram: 7 services, 7 edges:
      • the rest as in the previous step.
    • 5 labelled values:
      • Mode: iptables; IPVS uses round robin;
      • Load balancer: equal share per healthy node;
      • Health check header: X-Load-Balancing-Endpoint-Weight;
      • Topology-aware routing: not modelled;
      • Session affinity: not modelled.
  7. The pod sees the node’s address, not the client’s

    Node 3 swaps 198.51.100.79 for its own address, 10.240.0.3.

    Under Cluster, kube-proxy marks every outside request for source NAT, in case it crosses nodes. Node 3 replaces the client’s address, 198.51.100.79, with its own, 10.240.0.3, and pod b sees that. Requests that stay on their node are rewritten too.

Check yourself

  1. With pods placed 3, 1, 0 on three nodes and externalTrafficPolicy Local, why does pod d get three times the requests of pod a?

    Show the answer

    Node 3 runs no pod and fails the health check, so the load balancer gives Node 1 and Node 2 half each. Node 1 splits its half three ways (1/6 per pod); Node 2 gives all of its half to pod d.

  2. A node’s iptables chain lists three pods. With what probabilities do its rules match, and what share does each pod get?

    Show the answer

    1/3, then 1/2, then always: rule i of n matches with probability 1/(n−i), so each pod gets 1/3 of what the node receives.

  3. With pods placed 2, 2, 0, are Local’s shares even?

    Show the answer

    Yes. Node 1 and Node 2 each get half and each splits it two ways, so every pod gets 1/4: Local is even when every node with pods runs the same number.

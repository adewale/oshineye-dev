Why build the page before readers open it?

The token-bucket page offers 1, 2, 4 tokens a second, the only rates its reader can choose. R10 succeeds in all three, so its caption says “R10 is accepted at every rate”. Would that sentence survive a reader typing 0.1?

  2. At 0.1 tokens a second, R10 finds 0.5 tokens and is refused

    The sentence holds at every rate the page built and fails at one it never built.

    At 0.1 tokens a second, R10 still needs a whole token. After five seconds only 0.5 tokens have come back, so R10 gets 429. The caption described the offered inputs, not arbitrary rates. Rayner builds every scenario before anyone reads it, so rayner check can test each one and the author can read it, and a reader can open only a scenario the build made.

  3. The build made 3 scenarios, and a link opens one of them

    A link naming 0.1 matches no scenario, so the page opens the default, 2 tokens a second.

    The rate setting lists 3 options, so the build ran the scene once for each and rayner check tested each of the 3 scenarios; R10 is accepted in all three. A link picks a scenario by naming its option: ?rate=4 opens the 4-token scenario. ?rate=0.1 matches no option, so Rayner refuses it with “Unknown rate option: 0.1” and opens the default scenario, 2 tokens a second. The 0.1 row from the last step exists in this explainer, not on the token-bucket page.

That gives an author a finite set of outcomes to inspect, but publishing a prepared page still does not make an unchecked caption true for arbitrary inputs.

  5. 3 pod placements × 2 traffic policies make 6 scenarios to build

    Every combination of options is a scenario the build makes and rayner check tests.

    Prepared inputs have a cost: settings multiply. 2 policies combined with 3 pod placements produce 6 scenarios, and another setting multiplies that collection again. Finite review becomes more work as the number of combinations grows.

Check yourself

  1. On the token bucket page, R8 and R9 arrive together at 1 s. If its author moved R10 from 5 s to 1.5 s, at which offered rate would ‘R10 is accepted at every rate’ become false, and could a reader see the false sentence?

    Show the answer

    At 1 token a second. There R8 spends the one token that has come back by 1 s, so at 1.5 s the bucket holds half a token and R10 gets 429; at 2 and 4 tokens a second it is still accepted. A reader could see it only if the author published without reading that scenario, because 1 token a second is a scenario the build makes and the author can run and read.

  2. Someone shares a link to the token bucket page that ends in ?rate=0.1. What does the reader see, and do they meet the false sentence about R10?

    Show the answer

    The player looks for 0.1 among the rates the scene lists, finds none, and opens the default scenario, 2 tokens a second, with the notice “Unknown rate option: 0.1. Showing the default scenario.” The reader sees a scenario the author ran, where R10 is accepted; the 0.1 row exists only in this explainer.

  3. The traffic-policy page has two policies and three pod placements. Its author wants a third setting, the number of nodes, with four values. How many scenarios would the build make and the author need to read, and when is such a setting worth adding?

    Show the answer

    Twenty-four: 2 × 3 × 4. Each is built, checked and must be read before publishing, so a setting earns its place when one of its values changes what the page concludes, not merely a number on it.

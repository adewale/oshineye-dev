What does Git store when a file changes?

hello.txt contains hello followed by a newline. Git hashes its type-and-length header together with those content bytes; the resulting id names a blob. The blob stores content independently of the file name. What must be written when the next commit changes the file collection?

  2. A tree gives those bytes a name

    The name hello.txt is in the tree entry, not in the blob.

    A tree associates the name hello.txt and its mode with the blob’s id. The same content object can therefore be named by different trees without copying it. Hashing the tree’s own bytes gives that collection of names and references an id too.

Check yourself

  1. Adding world.txt leaves hello’s content unchanged. Why does the tree still need a new id when hello’s blob does not?

    Show the answer

    The tree’s bytes gain an entry for world.txt, so its content changes and gets a new id. Hello’s bytes stay unchanged, so the new tree can name the existing hello blob.

  2. If the second commit edits hello.txt to “hello again” instead, which ids change, and what happens to commit one’s objects?

    Show the answer

    The blob’s, the tree’s and the commit’s: each object holds the id of the one below it. Commit one’s blob, tree and commit stay in the store unchanged, reachable through commit two’s parent line.

  3. If main moves back to commit one, must Git change either commit’s content objects?

    Show the answer

    No. Moving main changes a reference, not the immutable objects it names. It selects a different existing snapshot without rewriting its blobs, tree or commit.

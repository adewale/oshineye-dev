Can an agent use a key it never sees?

The app needs API_KEY in its environment. Printing that value for the agent would also put it into the conversation, though the agent needs only to choose the credential and start the app. What can name the credential without exposing its value?

Transcript

  1. An agent must start an app with a key it should never read

    what could the agent pass along instead of the key?

    The app needs API_KEY in its environment. Printing that value for the agent would also put it into the conversation, though the agent needs only to choose the credential and start the app. What can name the credential without exposing its value?

    • Agent. ?. Application. needs API_KEY. must not read. the value.
  2. Answer: hand over a reference, and let op swap in the value

    The agent passes op://Personal/Cloud API/credential; op gives its value to the app.

    The agent handles only an op:// reference, and op puts the value into the app’s environment. The reference names a vault, item and field without containing the key. Authenticated op resolves that name when it starts the app. This keeps the value out of the launch request, but the app can still read or print its own environment.

    • Agent. op CLI. Application. op:// reference. secret value. op://Personal/Cloud API/credential.
  3. To pick a key, the agent searches titles, never values

    it asks for “cloud api” and the typo “databse”. What comes back?

    Title matching chooses the items without needing their field values. Here “cloud api” and “databse” search 3 sample titles. The later item-get reply can contain secret values; the wrapper discards them before returning references to the agent.

  4. Answer: a match for “cloud api”, a suggestion for “databse”

    Cloud API contains every word of “cloud api”; Database is 1 edit from “databse”.

    Cloud API contains the words in “cloud api”, so it matches. The typo “databse” has no match. Comparing its spelling with title words gives Database a score of 0.875, above the suggestion threshold. The fallback finds a likely name without comparing secret contents.

    Item list, then one item get for Cloud API and Database; one approval.

    find first lists titles, then fetches the selected items together. Upstream documents one desktop approval for this command. The agent still receives references rather than the secret-bearing item reply.

  6. find returns references and prints no secret value

    One reference per query; every sample value is searched for in the output.

    The returned strings identify a vault, item and field. Field values are discarded while the wrapper decodes op’s response. Those names let the agent select and launch the app without putting the key into the conversation; they do not themselves grant access to the vault.

  7. op starts the app with the key the agent never saw

    op resolves the API_KEY reference; the app gets its value and PATH.

    op resolves the reference and starts the app with API_KEY’s value. With desktop authentication there is no service-account token to remove. The reference keeps the value out of the agent’s launch request, but the app can still print what it receives.

Check yourself

  1. The agent searches for “databse”, which no title contains. What does find return, and why that item?

    Show the answer

    A suggestion, the Database reference. “databse” is one edit from “database”, so it scores 1 − 1/8 = 0.875, above the 0.6 threshold.

  2. The app prints API_KEY to stdout, and the agent reads stdout. Does passing a reference prevent that disclosure?

    Show the answer

    No. The app receives the resolved key and can print it. References keep field values out of find’s output and the launch request; they do not sandbox the app or redact its output.

  3. Does knowing an op:// reference let an unauthenticated process read that credential?

    Show the answer

    No. The reference names a location but supplies no authorization. An authenticated op process with the required access must resolve it.

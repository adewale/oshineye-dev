How does an agent know a poppy.json speaks for the shop?

Your agent is about to shop at www.example.com. In chapter 1 its first move was to read the shop’s poppy.json, a file that tells it where to send your requests and your tokens. But a JSON file is the easiest thing on the web to forge. Before you go on, think how you would make an agent believe that a file of yours speaks for example.com.

  2. The file speaks for the host that served it

    It must name that host itself.

    The agent fetches www.example.com/.well-known/poppy.json over HTTPS, and the shop redirects it to the same path on example.com, which is allowed. The file lists the ways in, at least one of them: the shop’s APIs, its website and its own agent, beside sign-in details, tasks and extensions. Its letterhead, organization.domain, says example.com, and the agent checks that this is the host that served it.

    • Server: shop, from www.example.com; 2 of 4 checks run. The agent fetched https://www.example.com/.well-known/poppy.json, which redirected it to https://example.com/.well-known/poppy.json. The shopfront's fascia reads example.com; the document's letterhead reads example.com. Checks: path passed (https://example.com/.well-known/poppy.json); domain passed (example.com); issuer not run; listing not run. No verdict yet.
  3. A handshake with the issuer

    The domain names its issuer; the issuer names it back.

    Who issues this shop’s tokens? example.com’s protected resource metadata, the signpost, names auth.example.com. The agent then asks the issuer, whose own metadata lists example.com among its domains. Each side points at the other, and from now on the Company is known by its issuer. That is the answer: The domain names its issuer and the issuer lists the domain back, and each check stops one way to impersonate the shop. Three forgers now try to get round one check each.

    • Server: shop, from www.example.com; 4 of 4 checks run. The agent fetched https://www.example.com/.well-known/poppy.json, which redirected it to https://example.com/.well-known/poppy.json. The shopfront's fascia reads example.com; the document's letterhead reads example.com. The signpost names the issuer https://auth.example.com, whose register lists the domain back. Checks: path passed (https://example.com/.well-known/poppy.json); domain passed (example.com); issuer passed (https://auth.example.com); listing passed (https://example.com). Verdict: the document speaks for the Company https://auth.example.com, which offers sign-in; User ID usr_Q7c1vK.
  4. A copy on a lookalike domain

    Refused: it names example.com, not examp1e.com.

    The first forger copies example.com’s file to examp1e.com and points the API address at its own server. The file is at the right path, over HTTPS, but it still says example.com and examp1e.com served it, so the agent refuses it at the domain check. Change the letterhead to examp1e.com and every check passes, even under example.com’s name and logo (draft 1.0, 10.3). The file then speaks for examp1e.com, a different Company, and noticing that domain falls to the agent.

    • Server: copy, from examp1e.com; 2 of 4 checks run. The agent fetched https://examp1e.com/.well-known/poppy.json. The shopfront's fascia reads examp1e.com; the document's letterhead reads example.com. Checks: path passed (https://examp1e.com/.well-known/poppy.json); domain refused; issuer not run; listing not run. Verdict: refused at the domain check, because the document names example.com, and examp1e.com served it.
  5. Claiming the shop’s issuer

    The issuer does not list evil.example.

    A cleverer forger is honest about its domain. evil.example serves a file naming evil.example, and its signpost names auth.example.com as its issuer. Believe that, and evil.example is the same Company as example.com: the agent would send it example.com’s User ID and tokens. But the issuer’s own register does not list evil.example. The handshake is missing its second side, and the agent refuses the file.

    • Server: claim, from evil.example; 4 of 4 checks run. The agent fetched https://evil.example/.well-known/poppy.json. The shopfront's fascia reads evil.example; the document's letterhead reads evil.example. The signpost names the issuer https://auth.example.com, whose register does not list the domain. Checks: path passed (https://evil.example/.well-known/poppy.json); domain passed (evil.example); issuer passed (https://auth.example.com); listing refused. Verdict: refused at the listing check, because https://auth.example.com does not list https://evil.example.
  6. A file uploaded to the real shop

    The path check alone stops it.

    The cleverest forger uploads a file naming example.com to example.com itself, at /uploads/poppy.json, and redirects deals.example’s well-known address to it. The file is served by example.com and names example.com, and example.com’s issuer lists example.com, so every other check would pass. The path check stops it: a redirect may go to any host, but it must end at /.well-known/poppy.json. Whoever controls that path speaks for the shop.

    • Server: upload, from deals.example; 1 of 4 checks run. The agent fetched https://deals.example/.well-known/poppy.json, which redirected it to https://example.com/uploads/poppy.json. The shopfront's fascia reads example.com. Checks: path refused; domain not run; issuer not run; listing not run. Verdict: refused at the path check, because the last URL, https://example.com/uploads/poppy.json, is not at /.well-known/poppy.json.
  7. A shop with no issuer

    Signed out: the domain is the Company.

    Some shops run no sign-in. corner.example’s metadata answers 404, which means it has no issuer, so there is no listing to ask for. The Company is then known by its own address, https://corner.example, and the agent can use it in signed-out Sessions only. Without an issuer, each domain is a Company of its own.

    • Server: small, from corner.example; 3 of 4 checks run. The agent fetched https://corner.example/.well-known/poppy.json. The shopfront's fascia reads corner.example; the document's letterhead reads corner.example. The domain’s metadata answered 404: no issuer. Checks: path passed (https://corner.example/.well-known/poppy.json); domain passed (corner.example); issuer passed (none); listing not run. Verdict: the document speaks for the Company https://corner.example, in signed-out Sessions only; User ID usr_c9Lw2e.
  8. An error is not “no issuer”

    The agent stops rather than fall back.

    Today example.com’s metadata times out. A careless agent would treat that like corner.example’s 404 and carry on with https://example.com as the Company. That would change the Company’s identifier, and with it the User ID the agent uses there. So after a timeout, an error status or invalid metadata the agent never falls back to the domain: it stops.

    • Server: outage, from example.com; 3 of 4 checks run. The agent fetched https://example.com/.well-known/poppy.json. The shopfront's fascia reads example.com; the document's letterhead reads example.com. The signpost’s arm stops short: the metadata timed out. Checks: path passed (https://example.com/.well-known/poppy.json); domain passed (example.com); issuer refused; listing not run. Verdict: refused at the issuer check, because the protected resource metadata timed out, and the agent does not fall back to the domain after an error.
  9. Two domains, one Company

    Now choose who serves the file.

    example.co.uk serves its own file and names the same issuer, which lists it too. So it is the same Company as example.com, with the same User ID, Sessions and refresh tokens. Each file also states its protocol version; the agent sends the one it chose as Poppy-Version, and a shop that no longer serves it answers 400 version_unsupported. Choose who serves the file and run the checks.

Check yourself

  1. A lookalike domain, examp1e.com, serves an exact copy of example.com's poppy.json at its own well-known path. Which check refuses it, and why?

    Show the answer

    The domain check: the document names example.com, and examp1e.com served it. A poppy.json speaks only for the host that served it.

  2. evil.example serves its own poppy.json, honestly naming evil.example, and its protected resource metadata names https://auth.example.com as its issuer. What stops it, and what would it get without that check?

    Show the answer

    The listing check: https://auth.example.com does not list https://evil.example. Without it, evil.example would be the same Company as example.com, and the agent would use User ID usr_Q7c1vK and example.com’s tokens there.

  3. Someone uploads a poppy.json naming example.com to example.com/uploads/, and makes deals.example's well-known URL redirect to it. Why does only one check catch this?

    Show the answer

    The last URL is on example.com, the uploaded file names example.com, and https://auth.example.com lists https://example.com, so the other three checks pass. Only the path check refuses it: the last URL, https://example.com/uploads/poppy.json, is not at /.well-known/poppy.json.

  4. The agent has used example.com before. Today example.com's protected resource metadata times out. May the agent treat example.com as a Company with no issuer until it answers?

    Show the answer

    No. The agent stops at the issuer check: the protected resource metadata timed out, and the agent does not fall back to the domain after an error. Falling back would make the Company https://example.com instead of https://auth.example.com, with new User IDs.

  5. example.co.uk serves its own poppy.json, and its metadata names https://auth.example.com, which lists it. What User ID does the agent use there?

    Show the answer

    usr_Q7c1vK, the same as at example.com: the two domains share the issuer https://auth.example.com, so they are one Company.

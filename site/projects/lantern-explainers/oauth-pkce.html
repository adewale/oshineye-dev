Why stealing an authorization code is not enough

PKCE protects public clients, such as mobile and desktop apps, which cannot keep a client secret. The client generates a random verifier, and the S256 challenge is the base64url SHA-256 of it. The card starts from RFC 7636’s example verifier.

Show an attacker: Yes

  1. The client keeps the verifier and sends only its challenge

    PKCE protects public clients, such as mobile and desktop apps, which cannot keep a client secret. The client generates a random verifier, and the S256 challenge is the base64url SHA-256 of it. The card starts from RFC 7636’s example verifier.

    • Flowchart: 3 nodes, 2 links:
      • code_verifier → 32-byte digest: SHA-256 (travelled);
      • 32-byte digest → code_challenge: base64url (travelled);
      • code_challenge (marked);
      • code_verifier;
      • 32-byte digest.
    • 3 labelled values:
      • code_challenge: E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM (marked);
      • code_verifier: dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk;
      • SHA-256 (hex): 13d31e961a1ad8ec2f16b10c4c982e0876a878ad6df144566ee1894acb70f9c3.
  2. The authorization request carries the challenge and S256

    The client sends the challenge and the S256 method in the authorization request, through the user’s browser, while the verifier stays with the client, as the card’s last row shows. The user then signs in and consents at the auth server.

    • Sequence diagram: 3 participants, 1 message:
      • Client → Auth server: Authorize request + code_challenge (carries the challenge);
      • Client;
      • Auth server;
      • Malicious app.
    • 3 labelled values:
      • code_challenge: E9Melhoa2Owv… (marked);
      • method: S256;
      • code_verifier: not sent.
  3. The redirect carries a short-lived code bound to the challenge

    The server stores the challenge with a short-lived code and redirects the browser back to the client. Because the verifier never travelled, anyone who intercepts this redirect gets only the code, which must still be exchanged for an access token.

    • Sequence diagram: 3 participants, 2 messages:
      • Client → Auth server: Authorize request + code_challenge (carries the challenge);
      • Auth server → Client: Redirect with code (carries the code);
      • Client;
      • Auth server;
      • Malicious app.
    • 2 labelled values:
      • bound challenge: E9Melhoa2Owv… (marked);
      • code_verifier: not in it.
  4. A stolen code fails without the verifier

    Another app on the device registered the client’s custom URI scheme, so the operating system handed it the redirect and its code (RFC 7636 §1). It has to guess the verifier; S256 of the guess does not match the bound challenge, so the server answers invalid_grant.

    • Sequence diagram: 3 participants, 5 messages:
      • Client → Auth server: Authorize request + code_challenge (carries the challenge);
      • Auth server → Client: Redirect with code (carries the code);
      • Auth server → Malicious app: Redirect via the shared URI scheme (attack);
      • Malicious app → Auth server: Token request: code + a guess (attack);
      • Auth server → Malicious app: invalid_grant (attack);
      • Client;
      • Auth server;
      • Malicious app.
    • 4 labelled values:
      • match: false (marked);
      • guessed verifier: attacker-doe…
      • S256(guess): X4OLkcBHvNsG…
      • bound challenge: E9Melhoa2Owv…
  5. The token endpoint returns a token only when S256(verifier) matches

    The real client sends the code with the original verifier. The server computes S256 of the verifier, finds that it matches the challenge stored with the code, and returns an access token once its usual code and client checks also pass.

    • Sequence diagram: 3 participants, 7 messages:
      • Client → Auth server: Authorize request + code_challenge (carries the challenge);
      • Auth server → Client: Redirect with code (carries the code);
      • Auth server → Malicious app: Redirect via the shared URI scheme (attack);
      • Malicious app → Auth server: Token request: code + a guess (attack);
      • Auth server → Malicious app: invalid_grant (attack);
      • Client → Auth server: Token request: code + code_verifier (accepted);
      • Auth server → Client: Access token (accepted);
      • Client;
      • Auth server;
      • Malicious app.
    • 4 labelled values:
      • match: true (marked);
      • code_verifier: dBjftJeZ4CVP…
      • S256(verifier): E9Melhoa2Owv…
      • bound challenge: E9Melhoa2Owv…
  6. The verifier never travels where the code does

    The challenge and the code pass through the browser and the operating system, where another app can read them. The verifier, 32 random bytes, goes only in the client’s own TLS request to the token endpoint. S256 cannot be reversed, so the challenge and the code alone cannot be exchanged.

    • Sequence diagram: 3 participants, 7 messages:
      • Client → Auth server: Authorize request + code_challenge (readable on the device);
      • Auth server → Client: Redirect with code (readable on the device);
      • Auth server → Malicious app: Redirect via the shared URI scheme (readable on the device);
      • Client → Auth server: Token request: code + code_verifier (direct TLS);
      • Client;
      • Auth server;
      • Malicious app;
      • Malicious app → Auth server: Token request: code + a guess;
      • Auth server → Malicious app: invalid_grant;
      • Auth server → Client: Access token.
    • 3 labelled values:
      • Direct, TLS: verifier (marked);
      • Via browser: challenge, code;
      • Verifier: 32 random bytes.
